# Verification package: parity on a subcube

Scripts and outputs behind the [subcube-parity note](../../subcube-parity.md). Each entry says what it checks and which section of the note it supports:

- [§1](../../subcube-parity.md#1-parity-on-a-subcube-is-exponentially-hard) Parity on a subcube is exponentially hard;
- [§2](../../subcube-parity.md#2-two-head-networks) Two-head networks;
- [§3](../../subcube-parity.md#3-gradient-descent-on-the-staircase-or-parity-target) Gradient descent on the staircase-or-parity target;
- [§4](../../subcube-parity.md#4-why-both-halves-are-needed) Why both halves are needed;
- [§5](../../subcube-parity.md#5-targets-without-a-parity-subcube) Targets without a parity subcube.

No proof in the note rests on these scripts. The exact and exhaustive checks run at small $`d`$ and guard against slips in the algebra and bookkeeping. They say nothing about asymptotics. The training runs are numerical evidence at $`19\le d\le 50`$ only.

**Running.** Run each script from its own folder with `python3 -I <script>.py > <script>.txt`. Every script except those in `numerics/` only prints to standard output. Requirements: Python 3 with NumPy, SciPy, mpmath and PyTorch. The reruns below used Python 3.13.16, NumPy 2.5.3, SciPy 1.18.1, mpmath 1.3.0 and PyTorch 2.14.1 on one CPU core each. Times are wall-clock times on a machine shared with two training jobs.

**Reruns.** Every script in this folder, `staircase/` and `symmetric/` was rerun from its folder in the repository on 20 October 2026, and its output was saved as the `.txt` next to it. Where an earlier output existed, it was compared with the new one. The comparison is given in the last column of each table. The training runs in `numerics/` were not rerun as a whole, since they take hours; see [numerics](#numerics).

These scripts were written by AI agents for this note and checked as described in the [review record](review.md); they are research code, not a library. Some comments still carry claim labels from drafting.

## `staircase/`: the sign-staircase alone

The sign-staircase is $`f_d=\mathrm{sign}(x_1+x_1x_2+\cdots+x_1\cdots x_d)`$, $`d`$ odd. These scripts check the claims that it is as close to low-degree threshold functions as parity is, and that it is not a restriction parity. No earlier outputs were saved, so there is nothing to compare.

| file | what it checks | note | rerun |
|---|---|---|---|

| `v2_restr.py` | Every restriction at $`d=5,7,9`$ and one weighted case at $`d=7`$. Whenever a restriction equals $`\pm`$ a parity of free coordinates, the free set is a prefix of the free coordinates and its coefficient dominates the others. No violations. | §4, §5 | 2 s |
| `v3_smooth.py` | The prefix-parity smoothing lemma: over the grid, the construction's degree divided by $`\sqrt{d\log(4/\varepsilon)}`$ is at most about 9.7, below the proved constant 18. ## `symmetric/`: symmetric targets

Symmetric targets are functions of $`\sum_ix_i`$. These scripts check the claims about readout training on fixed features, the Rademacher-weight kernel and the tied random restriction. Earlier outputs were saved as `.out` files, which are not included in this package; the comparison was made with them when the package was assembled. Reruns used default BLAS threading; with one thread the last digits of one unrounded eigenvalue in `v1.txt` differ.

**Changes made when copying.** In the JSON summaries and the first and last lines of the logs, the absolute path of the scratch folder was removed from the `json` argument, leaving `runs/<name>.json`. Nothing else was changed. Scratch paths were removed from the docstrings and comments of the scripts (some drafting labels remain, as noted above), and `walsh_checks.py` received a docstring. `greedy_learner.py` now takes its list of dimensions as an argument, with default `31 63`; its original loop also listed $`d=127`$, which was never run. No other line of computation changed.

**Runs and restarts.** All 36 entries of `jobs.txt` have finished, and each has a JSON summary and a log in `runs/`. Twenty had finished when the package was assembled, at about 04:20 UTC on 20 October 2026, and the other 16 were added in the same way by 17:22 UTC. The machine was restarted several times while the queue ran; every run interrupted by a restart was started again from the beginning with the same seed, and only complete runs are included. `jobs.txt` lists the entries in their final queue order. To add a run, copy its `runs/<name>.json` and its log here, remove the absolute path from the `json` argument, and rerun `make_tables.py`.

**Reproducibility of the training runs.** Three short runs were repeated with the copied `gd_train2.py`, on the same software and machine type: `par1L31def_s1`, `par1L19_s1` and `mix19_s1`. Every evaluation line of the new logs equals the original apart from wall time, and so does every field of the JSON summaries. Training is deterministic for a fixed seed on one CPU thread. Other PyTorch versions or hardware may change the numbers slightly. The longer runs were not repeated.

**Caveats.**

- Runs at $`d\le35`$ cannot distinguish polynomial from exponential growth in $`d`$.
- The control target is learned at small $`d`$: by the plain MLP at $`d=21`$ with default initialization, and by the Gaussian-initialized two-head network at $`d=19`$ and $`23`$. Within the budgets it is not learned from $`d=27`$ on.
- With default initialization at $`D\le22`$, training draws cover most of the $`2^D`$ inputs, so those test errors partly measure memorization. The Gaussian-initialization runs exclude the test points from training.
- Parity alone, one hidden layer of width 1024. With PyTorch's default initialization it is learned at $`d=20,30,31`$ and not at $`d=40,50`$ within $`1.5\cdot10^7`$ samples. With Gaussian weights of variance $`1/\mathrm{fan_{in}}`$ and zero biases it is learned at $`d=19,23,27`$ (two seeds at $`d=27`$), but not at $`d=31`$ within $`1.5\cdot10^8`$ samples. With the default initialization it is not learned at $`d=35`$ within $`6\cdot10^7`$ samples. At $`d=31`$ Gaussian weights also fail within $`3\cdot10^7`$ samples with default biases, or with the default's variance $`1/(3\,\mathrm{fan_{in}})`$, while uniform default weights with zero biases succeed. Each of these is a single seed, except two seeds for the default at $`d=31`$ and for Gaussian weights at $`d=27`$.
- Parity alone on the three-layer trunk with one readout and Gaussian initialization is not learned at any of $`d=19,23,27,31`$ within the budgets, while the two-head trunk learns the parity half of $`f^*`$ at each of these $`d`$. The plain MLP with Gaussian initialization learns the parity half of $`f^*`$ only at $`d=19`$. The parity-alone trunk runs and the plain-MLP runs are single seeds.
